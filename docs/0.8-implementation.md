# The Cuelist 0.8 — Architecture and Integration Preview

**Development version:** `0.8.0-alpha.1`. **Project schema:** v10, unchanged. This is not a finished 0.8 release or a certified show-control system.

## Architecture improvements delivered

- `src/ProjectMediaLoader.h/.cpp`: audio media preparation is separate from JUCE UI components; repeated path references share immutable decoded audio, and PCM budget failures do not replace a prepared result.
- `src/ProjectSafety.h/.cpp`: the bounded `RecoveryCheckpointWriter` coalesces pending snapshots, writes checkpoints atomically on a worker and drains before save/discard/shutdown. Model validation and JSON serialization remain on the UI thread and could be moved further in a future iteration.
- `src/DeviceIdentity.h`: the MIDI input/output discovery policy matches only the saved device identifier; if a port is missing, another device is never chosen as a silent fallback.
- `src/TransportTiming.h`: MIDI and OSC share the exact same monotonic origin for events in a particular audio callback, with timestamp conversion based on sample offsets.

## Audio, MIDI and OSC stability

- Failed WAV/MP3 imports no longer panic running audio before the file has been decoded and checked against the memory budget.
- When a configured MIDI **input** disappears, held UI input states are discarded. Its same ID is retried when the system reports it available; reconnection never automatically issues GO.
- The MIDI **output** reconnect routine uses the same exact-ID policy and prevents old note events from replaying on a newly opened port. PANIC/note-off behavior remains available.
- Output diagnostic counts record messages sent, dropped and dispatched more than 10 milliseconds after their scheduled time. The delay threshold measures **software worker dispatch** relative to the audio clock, not when a physical synthesizer or network target actually responds.
- Automated regression tests cover audio deduplication, preparation rollback, checkpoint concurrency/flush, fake MIDI inventories and actual localhost OSC UDP endpoint switching.

## Operator-run Windows hardware probe

From the repository folder, open PowerShell and run:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/hardware-check.ps1
powershell -ExecutionPolicy Bypass -File scripts/hardware-check.ps1 -OscLoopback
```

The first prints audio API/device names and MIDI input/output IDs without opening MIDI outputs or sending MIDI notes. The second additionally sends **one** OSC test packet to a temporary local UDP receiver at `127.0.0.1` and compares the received bytes. It never sends packets to external show hardware. Reports are saved to `build/hardware-reports/`. This tool is optional and separate from `The Cuelist.exe`, and is not shipped in the portable release package.

## Physical device acceptance checklist (not yet completed)

1. Rehearse with all actual Windows audio interfaces, MIDI controllers, synthesizers and the intended OSC receiving applications. Run Preflight before the test.
2. Verify GO, Stop, Panic and independent overlap under real multichannel audio. Exercise pause, repeat, the Inspector, Control Sets, and the MIDI piano roll.
3. Remove the configured MIDI input while a mapping is active; reconnect the same port and confirm input resumes but GO does not fire unexpectedly. Attach a different controller and confirm it is **not** selected.
4. Disconnect a MIDI output while notes are scheduled; reconnect and check that old notes are not replayed, note-offs are safe and no hung notes remain. Record device-specific reconnection time.
5. Test OSC destination software stopping/restarting and IP/port changes. The localhost probe confirms the packet encoder and UDP transmission only; it is not a receiver availability/acknowledgement protocol.
6. Record measured event dispatch jitter and **external** output latency under load. Use independent timestamp equipment or OSC receiver timestamps; keep both results separate.
7. Run several-hour shows with different cue densities; monitor CPU, peak memory, dropped packets and device reconnection counters. Keep a log of Windows version, audio drivers and interface models.

## Remaining 0.8 work

The UI still performs project JSON encoding and full media file decode on its event thread; moving those preparations into cancellable, progress-reporting background work is the next architectural step. Complete device-specific error reporting, longer hardware-soak tests, failure-injection for unplugged interfaces and verified audio/MIDI/OSC latency require the actual show machine and external devices. There is no basis yet for claiming sample-accurate hardware MIDI or UDP delivery.
